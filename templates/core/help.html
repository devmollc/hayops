Support team guide

How this helpdesk works, end to end. All applications share this one dashboard — the Application column and filter tell them apart.

The queue

  • Every ticket from every application lands in the single Tickets queue.
  • Filter by status, priority, queue, application, or assignee; free-text search covers subject and reference number.
  • Save any filter combination as a saved view (personal or shared with the team).
  • New tickets start as new; they flip to open automatically when claimed, assigned, or first replied to by staff.

Working a ticket

  • Claim takes an unassigned ticket (safe under two agents clicking at once); or assign explicitly from the sidebar.
  • Public reply is emailed to the customer. Internal note is never visible outside the team.
  • The reply box and the create-ticket form both have Insert canned response and Insert KB article — see below.
  • Statuses: new → open → pending (waiting on customer) → resolved → closed. Resolving sends the customer a CSAT survey; other status changes send a status-update email.
  • Merge moves comments, attachments, and participants into the target ticket and marks the source as merged.
  • A banner warns you when another agent has the same ticket open.
  • If a customer lost their ticket link, use Resend access link on the ticket — it re-sends the confirmation email with a fresh magic link.

Canned responses & KB links

A canned response is a saved block of text you drop into a reply instead of retyping it. Both pickers sit above the send button on the reply box, and on the create-ticket form when you raise a ticket on a customer's behalf.

Using one

  • Click Insert canned response, type to search — it matches the title and the shortcut — then hit Insert.
  • The text is appended to whatever you have already written, so you can stack a greeting and an answer, and half-finished replies are never wiped.
  • Insert KB article works the same way and drops in the article's title and link. Comments are sent as plain text, so paste-in links stay clickable in the customer's mail client.
  • Edit after inserting. Canned text is a starting point, not the whole reply.

Adding a new one

  1. Open Canned Responses in the top menu and click New Response. You do not need an admin account — any staff user can add, edit or delete one, and they are shared with the whole team.
  2. Title — what you will search for. Keep it descriptive: Refund approved — processing times beats Refund.
  3. Body — the text itself, sent verbatim. There is no templating, so leave a blank to fill in (Hi ____,) rather than guessing a name.
  4. Queue — leave blank to offer it on every ticket. Pick a queue and it appears only on tickets in that queue.
  5. Shortcut — optional short alias, searched alongside the title. Handy for the ones you use daily.
  6. Save. The response is searchable from every reply box straight away.

A queued response is invisible everywhere else — including the create-ticket form.

That form has no queue chosen at the moment it loads, so only responses left on All queues appear there. If you write a response you want reachable from anywhere, leave the queue blank.

The Canned Responses page lists every response with its usage count, highest first — the quickest way to see which ones are earning their keep and which are dead weight. Edit and delete live there too.

Live updates & sound alerts

  • The queue and open ticket timelines refresh themselves every ~10 seconds — no reload needed.
  • The tab plays a short beep when a new ticket or a customer reply arrives anywhere in the system.
  • Mute/unmute with the 🔔 button in the nav; the setting sticks per browser. Browsers require one click anywhere on the page after loading before they allow sound.

How tickets arrive

  • Email — customers write to any address at an app's mail domain (e.g. support@mail.example.com). The domain decides which application the ticket belongs to. Replies thread back via the [HD-xxxx] subject tag; senders unknown to a ticket get a fresh ticket instead (guards against ref guessing). Spam/virus-flagged mail is quarantined and never becomes a ticket.
  • Widget — the in-app panel in each product. Users can browse their tickets, create, and reply. Submissions carry rich debugging context (see below).
  • Portal — each app's public support site (e.g. support.example.com) has a submit form, the app's KB articles, and the customer's magic-link ticket view with a reply box.

What customers (and you) receive

  • On creation: a branded acknowledgment carrying their magic link (30-day, read + reply access, no account needed).
  • On your public reply: the reply, branded per application, sent from ticket+hd-xxxx@<mail domain> so their answer threads back.
  • On status change: a status update; on resolve: the CSAT survey instead.
  • The team address receives an alert for every new ticket and every customer reply — the fallback if nobody has the dashboard open.

Widget context data

Tickets created through the widget show a Context section in the sidebar: the page the user was on, browser and platform, viewport/screen size, timezone, referrer, recent console errors captured from their session, an optional annotated screenshot (in attachments), and any state the host application chose to attach. Check it before asking the customer for reproduction details — the answer is often already there.

Knowledge base

  • Articles are written once in Knowledge Base.
  • Bodies are Markdown — see the cheatsheet. The editor puts a live HTML preview beside the body box, rendered exactly as the portal will render it, so what you see there is what the customer gets.
  • An article assigned to an application appears only on that app's portal; an article with no application is global and appears on every portal.
  • Portals render articles under the app's own branding automatically.
  • Only published articles are searchable from Insert KB article in a reply — a draft cannot be linked to a customer.

Markdown cheatsheet

What the knowledge base understands. The preview beside the editor is the same renderer the portal uses, so anything that looks right there is right.

You write You get
# Heading … ###### Heading Headings, biggest to smallest. Each gets a link anchor.
**bold**, *italic* bold, italic
- item or 1. item Bulleted or numbered list. Indent four spaces to nest.
[text](https://example.com) A link. A bare URL is not linked automatically — wrap it in angle brackets, <https://example.com>, or use the bracket form.
![alt text](https://example.com/pic.png) An image. There is no upload — the URL has to already be somewhere public.
`code` Inline code. Good for field names, filenames, error strings.
```python … ``` A fenced code block. The language is optional and only labels the block — nothing is colour-highlighted.
> quoted Blockquote.
--- Horizontal rule.
| a | b |
|---|---|
| 1 | 2 |		 A table. The --- row is required and separates the header from the body.
[TOC] A table of contents built from the article's headings, dropped in at that spot.

The two that catch people out

  • A single newline is not a line break. Two lines of text with nothing between them become one paragraph. Leave a blank line for a new paragraph, or end the line with two spaces to force a break.
  • Not everything from GitHub works here. ~~strikethrough~~, - [ ] task lists and footnotes render as literal text. Raw HTML, on the other hand, is passed straight through.

SLA & CSAT

  • SLA policies (per queue and/or application, with priority overrides) stamp first-response and resolution due dates on new tickets; compliance shows up in Reports.
  • CSAT surveys go out automatically when you resolve a ticket; ratings and comments feed the Reports dashboard.

QC testbench

The Testbench is the shared manual regression script for each application: areas of test cases (quoted in bug reports by key, e.g. ISO-03), each with its setup, numbered steps and expected result. Everyone works from the same board, and every result is kept.

Running a test pass

  1. Open Testbench in the top menu and pick the application.
  2. Click Start new run (top right) and give it a name and the build under test, e.g. v1.4.0 regression. Starting a run closes the previous one; its results stay in each case's history.
  3. Claim a case before you start so nobody else picks it up — your name appears on everyone's board within a few seconds. Release hands it back, and anyone can release a claim that was left behind.
  4. Write what you saw in the notes box, then click Pass, Fail or Blocked.
  5. Testing again after a fix? Record the case again. It adds a new entry instead of replacing the old one.

The Show filters narrow the board to cases not run, in progress, failed, release focus or P0. The Runs list opens past runs, read-only.

Priorities

  • P0 must work — a failure blocks the release.
  • P1 important — a failure needs a decision before release.
  • P2 lower risk — worth reporting, unlikely to block.
  • Release focus marks cases covering what this release changed. Run those first.

Filing a bug from a failed case

  1. Click the case's History link. Failed and blocked results have a File GitHub issue button, which opens a new GitHub issue filled in with the case, its steps, the expected result, your notes and a link back to the result.
  2. Add any screenshots to the GitHub issue and submit it — the testbench keeps notes, not files.
  3. Back on the history page, click Edit result and paste the issue's URL. The board then shows Issue #123 on that case.

No File GitHub issue button?

The application has no GitHub repository set. Django admin → Source Applications → the application → Testbench → GitHub repo, written as owner/name.

Adding and changing cases

  • The board's Manage panel has Add a test case and Add an area; every case has an Edit link. Steps go one per line.
  • Delete (on a case's history page) takes the case off the board but keeps its history. Its key can't be reused from the form, so a test's history never gets mixed up with a different test.
  • Import JSON loads a whole suite from a file and Download JSON saves the current one. Areas are matched by code and cases by key. Tick Delete cases that are not in the file to make the file the complete script. A file with any error imports nothing and lists what to fix.
  • How to write good cases — wording, priorities, what to cover — is in apps/testbench/qc_guide.md, the same guide Claude reads (below).

Claude & the MCP server

The helpdesk is an MCP server, so Claude — working in Claude Code in any application's repository — can read and update that application's testbench suite: download it, compare it with what the code does today, check a draft, and save it once you approve.

Connecting Claude Code

  1. Create a personal token on the API tokens page and copy it — it is shown only once. The token acts as you; delete it on that page to revoke it, and it stops working if your account is deactivated.
  2. In a terminal, once per machine (replace <token>): 
    claude mcp add --scope user --transport http helpdesk {{ request.scheme }}://{{ request.get_host }}/mcp \
  --header "Authorization: Bearer <token>"
  3. In Claude Code, type /mcp — helpdesk should be listed as connected.

What to ask for

  • Update an application's QC suite. From that application's repository, run the draft_qc_suite prompt from Claude Code's / menu, or just ask: "Update the acme QC suite for this release — billing changed." Claude reads the guide, downloads the suite, compares it with the code, validates its draft, and shows you the additions, edits and deletions before saving anything.
  • Find gaps. "Download the acme suite and list features that have no test cases."
  • Summarise a run. "What failed in the current acme run? Draft GitHub issues for the P0 failures."
  • Investigate one case. "Show me the history of ISO-03."

Claude's saves are real, and made as you.

They appear on the board straight away. Claude is instructed to validate and show you the change summary first — read it before you approve, especially a save that deletes cases not in the file, which can take many cases off the board at once. Deleted cases keep their history.

Scripts can use the same token with the REST API at /api/testbench/. Endpoints and examples are in docs/TESTBENCH.md.

Adding a new application

  1. Django admin → Source Applications → Add. Set name, slug, portal domain (support.<domain>), mail domain (mail.<domain>), branding, and the origins allowed to embed the widget.
  2. Have ops run just ses-setup <domain> (DNS + SES) and add the portal domain to the deployment config — details in the repo README.
  3. Embed the widget in the product using the app's API key/secret — integration guide in docs/INTEGRATE.md.

Branding edits take up to 5 minutes to appear. Each portal domain caches its application record for 5 minutes, so after you change a product name, primary color, logo, or email signature the portal and outgoing emails keep using the old values until the cache expires. Reload after 5 minutes before assuming an edit did not save.
